FUNDAMENTOS

De la topología al comportamiento

Con N procesos y M estados locales por proceso hay hasta MN combinaciones de estados locales. El estado global puede incluir también memoria compartida y canales. Las pruebas ejecutan algunas planificaciones. Un modelo permite razonar sobre todas las ejecuciones que admite, siempre dentro de sus supuestos.

Red marcada

N = (P, T, F, W, M₀). P y T son conjuntos finitos y disjuntos de lugares y transiciones. F ⊆ (P × T) ∪ (T × P). W asigna un entero positivo a cada arco. Un arco ausente tiene peso cero. Un marcado M asigna a cada lugar una cantidad entera no negativa de marcas. M₀ es el marcado inicial.

Habilitación y disparo

Con lugares por fila y transiciones por columna, Pre[p,t] = W(p,t) y Post[p,t] = W(t,p). La condición de habilitación es M ≥ Pre[:,t], componente a componente. El disparo es atómico y produce M′ = M − Pre[:,t] + Post[:,t]. El modelo básico carece de duraciones.

Incidencia e invariantes

C = Post − Pre. Si una secuencia realizable tiene vector de conteos σ, entonces M = M₀ + Cσ. La ecuación es necesaria y puede admitir soluciones sin una secuencia habilitada. Si yᵀC = 0, entonces yᵀM = yᵀM₀ para todo marcado alcanzable. Un autoarco puede dar una entrada cero en C y seguir exigiendo marcas en Pre.

Concurrencia, sincronización y conflicto

Dos transiciones distintas pueden dispararse conjuntamente si M cubre la suma de sus entradas. Un join exige todas sus entradas a la vez. Hay conflicto efectivo si ambas están habilitadas por separado y compiten por marcas insuficientes para el disparo conjunto. Dos arcos unitarios que comparten un lugar con dos marcas pueden dispararse juntos.

Propiedades de verificación

PropiedadQué se comprueba
AlcanzabilidadM ∈ R(M₀) cuando existe una secuencia habilitada de M₀ a M, incluso la vacía. Una traza hacia un marcado de error sirve de contraejemplo.
AcotaciónUn lugar es k-acotado si M(p) ≤ k en todo marcado alcanzable. Una red es acotada si todos sus lugares tienen una cota finita. Una red 1-acotada se llama segura en la terminología de Petri.
SafetyUna violación tiene un prefijo finito que la evidencia. Por ejemplo, alcanzar un marcado con dos procesos en la sección crítica. La 1-acotación es un caso particular de safety.
VivacidadUna transición es viva si desde cada marcado alcanzable existe una continuación que permite dispararla. La red es viva si lo son todas. La vivacidad deja abierta la posibilidad de inanición en una ejecución concreta. Una garantía de que cada solicitud finalmente se atiende requiere analizar las ejecuciones y la equidad.
ReversibilidadPara todo M ∈ R(M₀), se cumple M₀ ∈ R(M). Es una propiedad del marcado inicial. Volver al modelo inicial tampoco equivale automáticamente a recuperar datos reales.
Interbloqueo y progreso. Un marcado sin disparos habilitados es terminal. Si aún queda trabajo pendiente, representa un bloqueo en el modelo. «Nunca alcanzar un bloqueo no final» es safety. «Cada solicitud termina» es liveness sobre ejecuciones. Una traza con bloqueo puede refutar ambas garantías. En el caso de los robots, los pasillos ocupados producen exclusión mutua, retención y espera, no expropiación y espera circular.

Redes coloreadas

En una CPN, las marcas son valores tipados, el marcado de un lugar es un multiconjunto, y los arcos tienen expresiones. Una transición puede dispararse para una ligadura si las entradas requeridas están presentes y su guarda es verdadera. Por ejemplo, un buzón puede contener Mensaje { id, destino } y la guarda seleccionar un destino. La descripción puede ser compacta aunque el espacio de estados siga siendo grande o infinito.

Del requisito a la implementación

Definí los eventos y supuestos, construí la red, formulá las propiedades y buscá pruebas o contraejemplos. Para redes finitas, el grafo de alcanzabilidad permite decidir las propiedades anteriores. En redes sin cota, una BFS puede continuar indefinidamente. El árbol de cobertura puede detectar crecimiento mediante ω y responde preguntas de cobertura, como si se pueden alcanzar al menos n marcas, con una semántica distinta de la alcanzabilidad exacta. Contrastá luego las trazas con el código y las pruebas de integración.

REVISIÓN DE LAS FILMINAS

Cómo se corrigieron los modelos

  • Disparo y conflicto (6–7). Se indica el peso 2 cuando un disparo mueve dos marcas. Para el conflicto por un recurso unitario se dibuja una sola marca y arcos de peso 1. Los ejemplos de independencia y join tienen marcas iniciales explícitas.
  • Mutex (8). Los arcos del recurso van de Libre a cada adquisición y de cada liberación a Libre. Cada proceso comienza con una marca de control. La red de la práctica conserva Pre y Post para distinguir finalización de bloqueo. El ejemplo de Rust explicita la liberación por alcance del guard.
  • Productor–consumidor (9). El búfer empieza vacío con K marcas en Libres. Producir consume un espacio libre y crea un ocupado, y consumir invierte el movimiento. El conteo abstrae orden y contenido.
  • Actores (10). Se separan envío, recepción e inicio del manejo, y finalización del manejo. El buzón contiene mensajes pendientes, y el control Listo/Ocupado serializa al receptor. Un rendezvous exige emisor y receptor en el mismo disparo.
  • 2PC (11). Se separan votos, decisión durable y entrega por participante. 2PC es un protocolo de commit atómico. El ejemplo de bloqueo ocurre tras votar Sí y antes de conocer la decisión, bajo el supuesto de caída sin recuperación.
  • Verificación (12 y 14). Se distingue 1-acotación de safety en general, vivacidad de ausencia de inanición y finalización normal de bloqueo. Las garantías se refieren al modelo y a sus hipótesis.

1. ¿Por qué necesitamos Redes de Petri?

¿Qué limita al testing empírico en concurrencia? Explicá la explosión O(Mᴺ), los Heisenbugs y cómo el modelado formal ayuda a garantizar safety y liveness antes de programar.

Ver resolución

Las pruebas cubren muestras de órdenes, entradas y fallas. Un interleaving raro puede quedar fuera.

N procesos con M estados locales admiten hasta Mᴺ combinaciones de estados locales, aun antes de agregar colas o memoria. La sincronización puede reducir las combinaciones alcanzables.

Un Heisenbug cambia su manifestación al observarlo. Registrar eventos o ejecutar paso a paso puede cambiar la planificación que activa el defecto.

En el modelo se formula safety como exclusión de estados malos y liveness como eventualidad bajo supuestos explícitos. Se buscan contraejemplos, se prueban invariantes y se evalúa la correspondencia con la implementación.

2. Anatomía y semántica dinámica

En N = (P,T,F,W,M₀), explicá lugares, transiciones, marcas, arcos y pesos. Escribí la regla de habilitación, la ecuación del disparo y su interpretación atómica sin tiempo implícito. Relacioná el modelo con mutex, semáforos y variables de estado o guardas.

Ver resolución

Un lugar representa una condición o reserva de recursos. Una transición es un evento. Los arcos indican qué se consume y produce y sus pesos indican las cantidades. El marcado describe el estado.

Para cada p, M(p) ≥ Pre[p,t]. Si se dispara t, M′(p) = M(p) − Pre[p,t] + Post[p,t]. El estado cambia en un único paso sin estado intermedio observable ni duración asociada.

Un mutex libre tiene una marca. Un semáforo de k permisos empieza con k marcas y cada adquisición consume una. Un conjunto de lugares con una única marca codifica una variable de estado finita. Un autoarco prueba la presencia de marcas y las repone; una guarda de CPN puede examinar valores.

3. Exclusión mutua

¿Qué representa la marca en Mutex? Explicá por qué puede entrar un solo proceso a la vez, demostrá M(SC A) + M(SC B) ≤ 1 y relacioná el resultado con Arc<Mutex<T>> y RAII.

Ver resolución

La marca en Libre representa el permiso disponible. Cualquier adquisición toma ese permiso y mueve la marca local de Pre a SC. La liberación lleva la marca local de SC a Post y devuelve el permiso.

Libre + SC A + SC B = 1 inicialmente y cada disparo conserva la suma. Como todos los términos son no negativos, SC A + SC B ≤ 1. El único terminal se alcanza cuando A y B ya terminaron.

Arc comparte la propiedad del objeto. Mutex sincroniza el acceso. MutexGuard libera el lock al destruirse. Mantenerlo indefinidamente o adquirir varios locks en órdenes incompatibles puede impedir el progreso.

4. Productor–consumidor

En un búfer acotado de capacidad K, identificá productor, consumidor, búfer, espacios libres y ocupados. ¿Cómo se evitan overflow y underflow? Obtené un invariante y relacioná el modelo con la sincronización clásica.

Ver resolución

Producir toma una marca de Libres y agrega una a Ocupados. Consumir hace lo inverso. El estado del búfer se representa con ambos lugares. Comienza en (K,0).

Con K ≥ 1, Libres + Ocupados = K. Con cero libres no se produce; con cero ocupados no se consume. El invariante acota ambos lugares por K.

La red abstrae los dos semáforos de disponibilidad. Si la implementación manipula un búfer compartido mediante varias operaciones, hay que proteger también la actualización de su estructura. El contador abstrae el orden de los mensajes.

5. Modelo de actores

¿Qué representan el buzón y sus marcas? Explicá qué supuestos de la topología evitan carreras de datos y relacioná el modelo con mpsc asíncrono en Rust.

Ver resolución

El buzón representa mensajes disponibles. Enviar añade una marca y recibir la consume. En la CPN cada marca puede portar el mensaje.

Listo + Ocupado = 1 serializa el manejo en B, y cada actor modifica su estado privado. La ausencia de memoria mutable compartida evita carreras de datos entre actores bajo ese diseño. El orden de llegada puede seguir afectando el resultado.

En Rust, Sender envía valores y Receiver los entrega a la tarea que posee el estado. El envío mueve el valor salvo que se decida copiarlo o compartir una referencia con sincronización.

6. Two-Phase Commit (2PC)

Identificá lugares y transiciones del coordinador, participantes, Prepared, commit y abort. ¿Qué pasa con las marcas si el coordinador cae después de la votación? ¿Cómo se representa el bloqueo y qué safety se conserva?

Ver resolución

Preparar activa la coordinación y habilita un voto por participante. Sí mueve la marca a Prepared. Tras dos Sí se puede tomar la decisión durable Commit. Las combinaciones con al menos un No habilitan Abort en el modelo. La decisión global habilita las entregas por separado.

Con ambos Sí, Caer consume Coord. activo y conserva las marcas en Prepared. Sin recuperación ni decisión durable, el marcado Caído + A preparado + B preparado tiene grado de salida cero, con acciones de aplicación todavía pendientes.

El control del coordinador habilita a lo sumo una decisión. Las transiciones que aplican commit requieren la decisión Commit y las que aplican abort requieren Abort. Se preservan el acuerdo y la condición de que el commit requiere votos afirmativos.

7. Propiedades formales

Definí alcanzabilidad, acotación, safety o 1-acotación, vivacidad y reversibilidad. Indicá qué problema detecta cada una y da un ejemplo. Priorizá una propiedad para banca, interbloqueo ferroviario, IoT masivo y un servidor web concurrente.

Ver resolución

Alcanzabilidad detecta si un error es posible, por ejemplo dos trenes en un tramo. Acotación limita la ocupación de un buzón. 1-acotación impide dos marcas en un lugar que representa un permiso unitario. Safety expresa también condiciones entre varios lugares, como la exclusión de dos rutas incompatibles.

Vivacidad formal comprueba que consumir pueda volver a ocurrir desde cualquier marcado alcanzable, lo cual detecta estados que lo inhabilitan para siempre. Reversibilidad exige poder retornar al inicial, por ejemplo vaciar un búfer y recuperar todos los permisos.

Banca: safety para impedir doble débito. Ferrocarril: safety para excluir rutas incompatibles. IoT: acotación para controlar el almacenamiento pendiente. Web: progreso de solicitudes bajo supuestos explícitos de disponibilidad y equidad para evitar esperas indefinidas.

En el orden (Libres,Ocupados), M₀ = (2,0) y solo se habilita Producir. Tras producir, M₁ = (1,1) y se habilitan ambas. Si volvés a producir, M₂ = (0,2) y solo se habilita Consumir.

Correspondencia entre Mutex y RAII
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let valor = Arc::new(Mutex::new(0));
    let hilos: Vec<_> = (0..2).map(|_| {
        let valor = Arc::clone(&valor);
        thread::spawn(move || {
            let mut guard = valor.lock().unwrap();
            *guard += 1;
        }) // Al salir del cuerpo, se libera el permiso.
    }).collect();
    for hilo in hilos {
        hilo.join().unwrap();
    }
    assert_eq!(*valor.lock().unwrap(), 2);
}
Ejercicio 10 · Motor y mutex

Descargar motor.rs

use std::collections::{HashSet, VecDeque};

struct PetriNet {
    marking: Vec<usize>,
    pre_matrix: Vec<Vec<usize>>,
    post_matrix: Vec<Vec<usize>>,
}

impl PetriNet {
    fn new(marking: Vec<usize>, pre: Vec<Vec<usize>>, post: Vec<Vec<usize>>) -> Self {
        assert_eq!(pre.len(), post.len());
        assert!(pre.iter().chain(&post).all(|row| row.len() == marking.len()));
        Self { marking, pre_matrix: pre, post_matrix: post }
    }

    fn enabled_at(&self, marking: &[usize], t: usize) -> bool {
        self.pre_matrix.get(t).is_some_and(|pre| {
            marking.iter().zip(pre).all(|(tokens, required)| tokens >= required)
        })
    }

    fn is_enabled(&self, t: usize) -> bool {
        self.enabled_at(&self.marking, t)
    }

    fn successor(&self, marking: &[usize], t: usize) -> Result<Vec<usize>, &'static str> {
        if !self.enabled_at(marking, t) {
            return Err("Transición inexistente o no habilitada");
        }
        marking.iter().enumerate().map(|(p, &tokens)| {
            (tokens - self.pre_matrix[t][p])
                .checked_add(self.post_matrix[t][p])
                .ok_or("Capacidad numérica excedida")
        }).collect()
    }

    fn fire(&mut self, t: usize) -> Result<(), &'static str> {
        let next = self.successor(&self.marking, t)?;
        self.marking = next;
        Ok(())
    }

    // Para las redes pequeñas y acotadas de esta actividad.
    fn reachable_markings(&self) -> Vec<Vec<usize>> {
        let mut queue = VecDeque::from([self.marking.clone()]);
        let mut visited = HashSet::from([self.marking.clone()]);
        let mut result = Vec::new();

        while let Some(marking) = queue.pop_front() {
            for t in 0..self.pre_matrix.len() {
                if self.enabled_at(&marking, t) {
                    let next = self.successor(&marking, t).expect("Marcado fuera de rango");
                    if visited.insert(next.clone()) {
                        queue.push_back(next);
                    }
                }
            }
            result.push(marking);
        }
        result
    }
}

fn main() {
    // Lugares: Pre A, SC A, Post A, Libre, Pre B, SC B, Post B.
    // Transiciones: adquirir A, liberar A, adquirir B, liberar B.
    let mut mutex = PetriNet::new(
        vec![1, 0, 0, 1, 1, 0, 0],
        vec![
            vec![1, 0, 0, 1, 0, 0, 0],
            vec![0, 1, 0, 0, 0, 0, 0],
            vec![0, 0, 0, 1, 1, 0, 0],
            vec![0, 0, 0, 0, 0, 1, 0],
        ],
        vec![
            vec![0, 1, 0, 0, 0, 0, 0],
            vec![0, 0, 1, 1, 0, 0, 0],
            vec![0, 0, 0, 0, 0, 1, 0],
            vec![0, 0, 0, 1, 0, 0, 1],
        ],
    );
    let reachable = mutex.reachable_markings();
    assert_eq!(reachable.len(), 8);
    for m in &reachable {
        assert_eq!(m[1] + m[3] + m[5], 1);
        assert!(m[1] + m[5] <= 1);
        println!("{m:?}");
    }
    assert!(mutex.is_enabled(0));
    mutex.fire(0).unwrap();
    assert!(!mutex.is_enabled(2));
}
Ejercicio 11 · Canal acotado

use std::{future::{poll_fn, Future}, task::Poll};
use tokio::sync::mpsc;

#[tokio::main(flavor = "current_thread")]
async fn main() {
    const CAPACIDAD: usize = 2;
    let (tx, mut rx) = mpsc::channel(CAPACIDAD);
    tx.send(10).await.unwrap();
    tx.send(20).await.unwrap();

    let pendiente = tx.send(30);
    tokio::pin!(pendiente);
    // Consultamos una vez el futuro con el receptor abierto y el búfer lleno.
    // Pending significa que send cedería la ejecución si se esperara con await.
    poll_fn(|cx| {
        assert!(pendiente.as_mut().poll(cx).is_pending());
        Poll::Ready(())
    }).await;

    // Recibir devuelve una plaza: Ocupados → Libres.
    assert_eq!(rx.recv().await, Some(10));
    // El envío usa la plaza devuelta: Libres → Ocupados.
    pendiente.await.unwrap();
    assert_eq!(rx.recv().await, Some(20));
    assert_eq!(rx.recv().await, Some(30));
}
Ejercicio 12 · Caída después del voto

Descargar dos_fases.rs

use std::time::Duration;
use tokio::{sync::oneshot, time::timeout};

#[derive(Debug, PartialEq)]
enum Decision { Commit, Abort }

#[derive(Debug, PartialEq)]
enum Estado { Prepared, Committed, Aborted }

async fn participante(
    voto_si: oneshot::Sender<()>,
    decision: oneshot::Receiver<Decision>,
) -> Estado {
    // Simula haber registrado Prepared de forma durable antes de votar Sí.
    voto_si.send(()).expect("Coordinador desconectado antes del voto");
    match timeout(Duration::from_secs(1), decision).await {
        Ok(Ok(Decision::Commit)) => Estado::Committed,
        Ok(Ok(Decision::Abort)) => Estado::Aborted,
        Ok(Err(_)) | Err(_) => Estado::Prepared,
    }
}

async fn escenario(decision: Option<Decision>) -> Estado {
    let (voto_tx, voto_rx) = oneshot::channel();
    let (decision_tx, decision_rx) = oneshot::channel();
    let tarea = tokio::spawn(participante(voto_tx, decision_rx));
    voto_rx.await.unwrap();
    if let Some(decision) = decision {
        decision_tx.send(decision).unwrap();
    } else {
        // El coordinador cae después del voto. El cierre es observable,
        // pero no contiene una decisión de la transacción.
        drop(decision_tx);
    }
    tarea.await.unwrap()
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let estado = escenario(None).await;
    assert_eq!(estado, Estado::Prepared);
    assert_eq!(escenario(Some(Decision::Commit)).await, Estado::Committed);
    assert_eq!(escenario(Some(Decision::Abort)).await, Estado::Aborted);
    println!("Tras la caída: {estado:?}. Hace falta resolver la decisión durable.");
}
